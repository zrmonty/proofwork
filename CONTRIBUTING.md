# Contributing to Proofwork

Start with a user outcome or reproducible friction: what the person tried, what happened, what was expected and what check distinguishes a repair. Use synthetic public examples. Never post customer records, credentials, private account paths or raw provider transcripts.

## Author guidance

Edit canonical shared assets and host adapters, then rebuild packages. Instructional text must be original to Proofwork's specification. A new skill needs a distinct uncovered trigger; conditional references are usually cheaper than another listed command. Entries stay within 600 words, references within 800. Preserve incumbent style, caller ownership and proportionate loading. No universal file/function line cap applies.

An entry states its outcome, trigger, decisions, evidence obligation and stopping condition. References deepen actual failure modes without repeating neighboring lenses. Link the existing owner instead of creating another coordinator. Principles supply short decision tests with observable consequences; playbooks combine owners without duplicating their rules.

For routing changes, add a failing exact case and a nearby false positive. For runtime changes, reproduce failure before repair. Evaluation fixtures need a broken baseline, failing visible/withheld acceptance checks and passing preservation checks. Do not disclose the oracle to the runner; document isolation limits.

## Verify and submit

Run `npm run check` and `npm run build:hooks`. Both host layouts must build and retain capability parity. Review generated changes. CI repeats gates and package parity on Windows and Ubuntu; native behavior needs separate host evidence. Honor repository commit conventions; feature sections require opt-in.

Describe the problem/result, meaningful checks, limits and initial/deferred context cost. Keep unrelated upgrades and policies out. Update affected command listings, references and scenarios. Use the [outcome protocol](docs/user-outcome-evaluation.md) for comparative claims.

## Production-user feedback

We seek opt-in volunteers who operate software with recovery, audit or access-control responsibilities. The outcome-feedback form accepts sanitized friction reports or volunteer interest. No private-codebase access is implied. Start with a public-safe bounded task. Read [the feedback loop](docs/early-user-feedback.md) before recording or publishing results.
