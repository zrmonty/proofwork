# Language fit

Select implementation technology from workload, safety, ecosystem and operating needs. No language or framework wins by habit. Pair with architecture-fit, which establishes whether components and boundaries are needed at all.

Inspect accepted direction, existing code, target platforms and owner. Separate systems, scripting/automation and fullstack/UI responsibilities without automatically creating three services. A trading dashboard, backtest tool and execution engine require different evidence. Vue versus React is a framework choice; either can use TypeScript.

Compare the incumbent, a simpler adequate arrangement and materially different credible alternatives. Give systems candidates such as Rust, C++ and C a fair evaluation where native control matters, while retaining other capable options. Consider Python and other scripting ecosystems, service language families, server-rendered HTML and relevant frontend frameworks. Verify current support and technical claims with primary sources.

Read [decision workflow](references/decision-workflow.md) for substantive choices, [systems and boundaries](references/systems-and-boundaries.md) for critical paths or mixed languages, and [frontend/application fit](references/frontend-and-application.md) for rendering and user journeys. Each additional language must justify its toolchain, deployment and data-contract cost. Never duplicate business authority across the boundary.

Recommend a supported fit with tradeoffs, excluded alternatives, decisive unknowns and an affordable next step. Performance claims need comparable measurements; absent benchmarks remain hypotheses. Choice alone does not authorize scaffolding, dependency changes or migration. Apply language guidance once the actual choice or file scope warrants it.
