# Frontend design

Make the interface feel deliberately designed for its content and audience. Commit to a clear visual idea;
carry it through real interaction states. A familiar component can be right; an interchangeable page needs a
stronger relationship between purpose, hierarchy and expression.

## Establish the design authority

Inspect the requested surface, primary journey, representative content, current rendering, tokens, components
and assets. Read existing product/design notes when relevant; their absence does not erase an established
identity. Preserve user-selected aesthetics and factual copy. Ask only for missing choices that materially
change the result; settle code-answerable questions by inspection.

Distinguish refinement from an authorized replacement. Refinement improves the incumbent system. A redesign
may replace its visual language while preserving product truth, useful behavior and public contracts. Do not
silently rebrand a spacing fix or turn an operational screen into a promotional page.

## Choose the work

Use [task approaches](references/task-approaches.md) to scope the request:

- New or unresolved composition: establish audience, content priority and one visual thesis; use
  [composition](references/composition.md). Compare two structural directions only when the choice matters.
- Critique or usability repair: identify observed friction, its consequence and the smallest useful correction;
  use [rendered review](references/rendered-review.md). Report-only requests authorize no edits.
- Visual refinement: select the weak dimension, preserve successful ones and use
  [visual expression](references/visual-expression.md), [type and color](references/type-and-color.md) or
  [motion](references/motion-and-feedback.md). More decoration is not the default answer.
- Shared foundations: extract repeated, proven roles from the existing implementation; use
  [interface craft](references/interface-craft.md). Avoid a speculative component library.

These are internal approaches, not additional commands. Follow the user's outcome without a menu ceremony.

## Build with conviction

Make one representative journey work before multiplying sections. Decide what leads, what supports it and
what can disappear. Use real content, coherent type/spacing/surface roles and appropriate assets. Distinction
can come from editorial rhythm, imagery, purposeful density or a strong interaction; rounded forms and open
reading areas are options, not a compulsory style.

Keep semantic controls, readable secondary text, visible focus, truthful state and recoverable errors.
Test narrow layouts, long content and reduced motion where relevant. Load
[journey continuity](references/journey-continuity.md) for navigation, dialogs or retained work, and
[detailed workflow](references/detailed-workflow.md) for substantial builds. Use humanizer for application copy.

## Inspect and finish

Build a complete slice, batch revealing desktop/narrow captures and interactions, fix material defects
jointly, then confirm. Default to one inspection and one confirmation; extra passes need a named unresolved
criterion, new evidence or user feedback. Stop preference cycling; never conceal a remaining functional defect.

Return the changed experience, selected direction, actual rendered/interaction observations and gaps.
Missing browser access leaves visual acceptance unverified. A build, mock or confident description does not
prove usability; never invent research, testimonials, asset rights or approval.
