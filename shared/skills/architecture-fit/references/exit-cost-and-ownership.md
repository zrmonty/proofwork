# Exit cost and operating ownership

Load when competing architectures appear equally capable, a vendor feature becomes central, or a proposal claims portability as its main benefit. Compare the burden of the actual arrangement, including the people who must recover it. This is a decision aid, not a requirement for provider-neutral code.

## Distinguish an exit from an abstraction

A generic storage interface can hide method names while leaving data shape, transaction semantics, permissions and recovery bound to one provider. Ask what must move in a credible exit: records, attachments, identifiers, credentials, scheduled work, client contracts and operator procedures as relevant. Name a concrete migration obstacle rather than calling a stack “locked in.”

Separating pure domain transitions from adapters helps readers understand effects. It does not make unlike persistence or delivery guarantees interchangeable. Preserve the chosen system's useful guarantees instead of designing a lowest-common-denominator interface for hypothetical alternatives.

Evaluate only exit paths material to this project. A short-lived internal tool may reasonably accept provider-specific features. A contractual export obligation or credible discontinuation risk can justify more preparation. Do not implement several adapters merely to demonstrate flexibility.

## Worked choice: member events

A small team needs signups, confirmation delivery and occasional CSV exports. One candidate is a managed platform with integrated identity and delivery; another is a smaller custom application with separate identity, mail and backup arrangements.

Compare the full workflow and responsible owner, not just subscription cost or package count. Does the managed platform export the required records and attachments? Can the team explain account ownership, denied access and recovery? Does the custom option make somebody maintain reconciliation and incident repair? Those obligations count even if implemented in a few scripts.

If the managed option fits and its exit burden is acceptable, retain its direct integration. If a required data export cannot preserve ownership or relationships, that can disqualify it despite an attractive prototype. A lightweight existing export path may address the issue without introducing a generic platform layer.

The decision is keep, replace, omit or defer with a reason. “We can switch later” is unsupported unless the material exit obligations are identified; “we need portability” is unsupported without a relevant requirement or risk.

## Ownership can decide a tie

Name who can update, restore and revoke access to each consequential component. A nominally simple deployment can be operationally fragile if one person's workstation is its only build or credential owner. Prefer the arrangement the actual team can sustain; do not add enterprise operations machinery to compensate for an unanswered ownership question.

Distinguish a provider's capability from the team's configured use of it. Available backups do not prove recoverability; available access controls do not prove appropriate permissions. Inspect the relevant configuration or procedure before crediting it in the comparison.

When one owner leaves, which existing supported mechanism transfers control? Treat that as a concrete operating question when ownership concentration is material. Do not request real credential values or create new accounts as part of a recommendation.

## Cheapest decisive evidence

- For an export requirement, inspect a sanitized representative export for identifiers, relationships and completeness; record what cannot be observed.
- For an operating advantage, inspect the current recovery/access procedure and the named owner rather than inferring competence from the brand.
- For a portability claim, trace one consequential operation and identify the semantics that the proposed replacement must preserve.

These observations support the specific choice, not a capacity or live-recovery certification. Record accepted dependence, likely switching work and the event that would reopen the decision. An architecture recommendation alone authorizes neither migration nor external changes.
