# Security-hardening specification

## Purpose and scope

Audit application security and fix reachable vulnerabilities at shared trust/enforcement boundaries. An audit-and-harden request authorizes scoped local repairs; read-only review remains read-only. Preserve valid behavior, user policy and host permissions. Original guidance; linked authoritative documentation grounds technical facts without importing instructional assets.

## Required decisions

- Identify snapshot, surface, actors, assets, trust boundaries and available evidence.
- Trace relevant authorization, injection, file/URL, exposure, dependency/build and resource-limit paths, including consumers and alternate routes.
- Distinguish confirmed defects, supported static findings, candidates, intentional behavior and gaps. Rank real impact without invented severity or quotas.
- Redact before tool output; never expose credential values, fragments or matching source lines.
- Correct the shared cause using incumbent mechanisms, pure policy/state decisions and current server enforcement. Preserve concurrency, cleanup and legitimate use.
- Add distinguishing regressions and apply existing type, coverage and 500-line gates. No suppressions or feature shutdown used to manufacture closure.
- Report fixed/verified, mitigated, unresolved and investigation status; real credential response and live operations remain separately authorized effects.

## Acceptance cases

1. Cross-tenant export: reproduce locally with synthetic identities, correct the authoritative query/policy and verify valid export plus denial with no prohibited disclosure.
2. Protected action has a client-only check: enforce permission at the actual server effect boundary; hidden controls or pure predicates alone fail.
3. Secret-bearing scanner output: configure redaction before inspection; report safe location/disposition and retain rotation as unresolved when unavailable.
4. URL validation precedes unrestricted redirects: identify remaining SSRF reachability rather than claiming the hostname regex settles it. No public-target probing.
5. Vulnerable locked dependency: consult current authoritative advisory, establish affected inclusion/use and verify the consumed corrected artifact; indiscriminate upgrade is insufficient.
6. A public static page has no private action: permit a supported clean verdict; do not invent authentication or a findings quota.
7. Missing runtime/scanner or destructive proof: use a supported bounded source trace and name the missing evidence; no fabricated verified closure.

## Evidence

Routing and package checks establish discovery structure only. Forward fixtures, live boundary behavior, artifact scanning and production response require their own observed evidence. No compliance or exhaustive-security certification follows from a clean audit.
