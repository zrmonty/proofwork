# Specification: brainstorm

## Purpose and contract

Shape a new project or unresolved idea into a useful direction before prescribing architecture or implementation. Inputs are the ordinary-language brief, repository/product context, supplied references, constraints and any accepted plan. The output is a concise working brief containing audience/outcome, primary journey, smallest useful slice, exclusions, assumptions and observable acceptance.

The skill owns product exploration. It recommends concrete alternatives when they expose a real decision, asks only consequential missing questions and labels assumptions. Architecture-fit owns consequential component and operating choices. Frontend-design and humanizer inform relevant experience/content work. Accepted direction and explicit implementation intent prevent unnecessary re-brainstorming.

## Acceptance cases

- A new volunteer app explores the actual coordinator/volunteer journey and a first useful slice before choosing a database.
- A supplied approved design with an implementation request returns to implementation rather than inventing another discovery workshop.
- A brainstorming-only request produces a direction without code writes or external publication.
- Two plausible audiences would need different journeys: ask that material question, continue independent context inspection and keep dependent choices provisional.
- A visual concept without browser access remains a proposal; no rendered-quality claim is made.
- An architecture uncertainty receives a brief and specific question for architecture-fit rather than a popular default stack.

These cases specify expected agent decisions. Packaging and router tests establish resource/routing behavior, not creativity, product demand or full agent-workflow quality.
