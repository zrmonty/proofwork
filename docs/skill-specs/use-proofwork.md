# Specification: use-proofwork

## Purpose and inputs

Own a scoped engineering outcome from discovery through integrated verification and authorized delivery, using delegation only when it creates useful independence. Inputs are the task, repository instructions and changes, design, native goal state, host capabilities, user limits and any prior run.

## Decision contract

The root discovers the installed runtime, runs the packaged router, reads selected guidance and corrects routing from inspected scope. It establishes observable criteria and explicit ownership before writes. Direct execution fits bounded work; substantial parallel work has agreed interfaces, independent ownership, sequential integration and independent correctness/maintainability review. Model mappings preserve user policy and do not imply cross-provider support.

Evidence identifies current content and its covered behavior. The coordinator validates worker artifacts and records reviewed results on the integrated identity, rather than mechanically relabeling stale evidence. Recovery inspects checkout identity, live workers and actual external state before retrying. Completion requires settled findings, collected modifying workers, current required evidence and authorized delivery; local guards and native goal lifecycle remain distinct.

Conditional detail lives in the skill's references/coordination.md and references/recovery.md. These give decisions and realistic examples; canonical record schemas remain in shared/contracts and scripts/README.md.

## Observable acceptance cases

- A one-function export bug runs routing, reproduces the failure and checks the fixed boundary without launching a ceremonial team or unrelated architecture work.
- An API/UI feature agrees shared fields, errors and states before dispatch; worker owners are disjoint, generated output has one owner, and combined navigation/error behavior is checked after integration.
- Two workers needing the same type do not concurrently edit it. The coordinator revises ownership or isolates their work and integrates sequentially.
- A worker pass at an earlier identity is not accepted as current proof after a behavior/dependency change. A dirty tree is not identified solely by HEAD.
- A latest failing criterion observation cannot be concealed by an older pass. Missing browser access leaves the visual criterion unproved while useful code checks continue.
- An interrupted push checks actual remote state before retrying. An uncertain PR/deployment effect is not assumed failed because a checkpoint lacks success.
- A copied/moved checkout starts a new run after inspection; stale worker identifiers and locks are reconciled rather than blindly reused or removed.
- A review-only task returns findings without edits or posting. An existing goal retains its objective; mode invocation creates no goal or scheduler, and limits produce incomplete state.
- Completion distinguishes the local guard's structural verdict from honest evidence, live ownership and native goal status. Commit delivery reads commit-features and validates the actual outgoing range.

## Evidence and boundaries

references/acceptance-changes.md covers changing requirements and new failure evidence inside an active run. Adding cancellation publication semantics revises UI/job integration criteria while unchanged serializer evidence may be retained through actual dependencies. The correction does not authorize deleting server records, cancelling unrelated jobs or creating another native goal. Live dependent owners receive the revised contract before writes, historical failures remain visible, and completion uses current acceptance rather than superseded intent.

Acceptance identifies user outcomes, preserved contracts and consequential failure evidence. The coordinator tracks semantic dependencies, not only disjoint paths, and makes the critical path visible before dispatch. A later user correction revises dependent criteria/assignments without discarding unaffected work. Resumed evidence is reused only through actual content/environment dependencies; next actions identify a specific uncertainty or criterion rather than a generic testing intention.

The coordinator verifies the actual changed contracts and any explicitly configured project policies. It reports the inspected scope and unresolved findings without claiming a universal codebase pass.

Review functions and files by clear naming, responsibility and understandable control flow, with no arbitrary length ceilings. Packaging validation proves resource structure only; never invent execution, installation, aliases or host support. Authority and evidence remain explicit.

Original authorship: this skill and its references were written to Proofwork's requirements and current runtime contract. No external skill text or workflow was imported or mechanically paraphrased. Acceptance cases above are specifications until actual evaluation records establish behavior.

## Skill-compression acceptance

The root owns engineering translation; users may supply ordinary intent without selecting skill names, patterns, models or verification methods. Load references/intent-and-judgment.md for experiential briefs, creative revisions and consequential choices. Preserve expert control and current authority. Completion remains evidence-bound.

Authored acceptance cases:
- An export brief names a missing final page without a test strategy: root traces consumers, defines preserved format/final-page criteria and selects regression/integration methods without demanding engineering vocabulary.
- A calmer publication brief produces a content-grounded provisional direction and an authorized reviewable slice; missing browser access remains an explicit visual-evidence gap.
- Simultaneous editing is unknown and changes correctness: ask about the actual editing workflow, recommend a mechanism from the answer and do not ask the user to design a locking algorithm.
- A cheaper hosting request does not silently weaken backups, buy a service or migrate data. Surface the consequence and actual missing authority.
- Expert requests for implementation reasoning receive traceable code and evidence; an intuitive default never suppresses inspection.

Evaluate newcomer task completion, avoidable technical choices delegated back, clarification burden, useful-slice latency and delivered defects on comparable tasks. These cases are requirements, not executed behavioral measurements or proof of improvement.

## Stage-aware routing

Choose the current stage from the prompt and actual context before implementation. New/unresolved projects use brainstorm; unresolved technical structure uses architecture-fit; approved constraints proceed to implementation. Bug fixes and focused changes preserve adequate incumbent architecture. Re-route the current subtask after a meaningful transition and record selected playbook/skills without replacing the overall objective or expanding authority.

Router tests exercise brainstorm, architecture and production-finishing playbooks, their persisted checkpoint values, approved-design implementation and new-project bug disambiguation. Keyword routing remains a starting recommendation; coordinator context resolves ambiguity. No mandatory phase chain or unattended transition is implemented.

## Language and framework selection

Route explicit language-fit and material language/framework choices to architecture with language-fit. Before scaffolding a new implementation, inspect unresolved technology decisions even when the brief names no language. Preserve adequate incumbent choices for focused work. Existing language files select implementation guidance, not permission to reopen the stack or favor TypeScript.

## Inspectable decisions and roles

The entry reads route explanations and selected principle files, naming a principle when it changes a decision.
Light stays bounded; overrides retain security/concurrency and executable behavior floors. Consequential choices and
independent reviews load model patterns conditionally. Configured roles respect observed host capabilities and budgets;
missing access remains explicit. Prototypes compare isolated artifacts; integrated candidates need fresh evidence.
