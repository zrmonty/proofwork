# Specification: language-fit

## Purpose and contract

Choose languages, runtimes and frameworks from project requirements across systems, scripting/automation and fullstack/UI work. Challenge habitual TypeScript/React defaults without replacing them with mandatory Rust/Python/Vue defaults. All credible options receive requirement-based consideration; the output is a ranked responsibility matrix, rationale, tradeoffs, evidence gaps, owner and smallest authorized next step.

Architecture-fit owns whether components/boundaries are needed. Language-fit owns the implementation technology for those responsibilities. Categories do not require three services or languages. Retain an adequate incumbent for focused changes; a recommendation does not authorize scaffolding, migration or deployment.

## Required decisions

Read ordinary intent, accepted scope and actual workload. Distinguish language, runtime, library, framework and rendering architecture. Compare sustained/burst throughput, tail latency/deadlines, memory, numeric/data semantics, native APIs, safety, failure/recovery, deployment, diagnostics, maintainability and migration costs. Ask only missing facts that change the decision. Verify consequential current claims in primary documentation.

Seriously compare Rust, C++ and C for a critical native throughput/latency responsibility, with other supported candidates remaining viable when evidence fits. Split trading administration/research/execution responsibilities instead of classifying the whole product as one hot path. Compare single-language and mixed-language arrangements, including marshalling, lifetime, schema, authority, cancellation and deployment costs. Preserve pure domain decisions and existing quality gates.

Use performance-increase for deciding empirical comparisons; show actual comparable metrics and practical interpretation when available. Greenfield hypotheses and unexecuted comparisons remain provisional. Missing bundled language guidance is explicit and does not select TypeScript by convenience.

## Authored acceptance cases

1. A trading dashboard with ordinary external API latency does not receive an automatic whole-product native rewrite.
2. A measured critical execution subsystem compares Rust/C++/C with applicable alternatives and preserves ordered/durable numeric decisions; UI/automation choices remain independent.
3. An incumbent C++ vendor SDK creates a concrete integration advantage; Rust is not selected by preference without examining the binding cost.
4. A Vue-versus-React request evaluates equal user journeys and production conditions, not a universal faster-framework claim or forced TypeScript choice.
5. A Python automation is chosen for required integrations and strict typed boundaries, with retry/idempotency/error behavior preserved; an existing-runtime script remains a serious alternative.
6. A Vue/Python/Rust proposal accounts for three toolchains and every seam; a simpler adequate single stack can win.
7. A no-rich-interaction publication considers server/static delivery with selective enhancement before a mandatory client framework.
8. Missing C/C++ specialist assets are disclosed and addressed through primary sources and checks rather than pretending guidance is bundled or silently defaulting to a covered language.
9. A focused bug fix in an adequate incumbent stack preserves that stack and does not reopen the language choice.
10. A prototype's unsupported hard-real-time claim stays unverified despite a favorable measured average.
11. A choice-only brief returns a reasoned decision, not scaffolded services or installed dependencies.
12. Multiple responsibilities share a business rule: preserve one authoritative owner and verify the combined consumer boundary after implementation.

Cases specify desired decisions, not executed benchmark or host-workflow evidence. Instructional assets are originally authored to these requirements.
