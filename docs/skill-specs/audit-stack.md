# Audit-stack specification

One coordinated entry loads security, dead-code, DRY, performance, TDD/coverage, architecture and maintainability lenses. Default invocation performs scoped local repairs; explicit report-only instructions preserve read-only behavior. Use the existing coordinator/runtime/goals; do not create a second scheduler or recursively dispatch the aggregate command. Originally authored guidance.

## Required decisions and acceptance cases

- Establish one audited surface, identity, supported configurations and baseline. Core lenses each receive an evidence-based status; reading instructions alone is not assessment.
- Merge repeated root causes, keeping distinct obligations. A vulnerable duplicated helper gets one finding/repair, with security and consumer checks preserved.
- Establish deadness before DRY extraction; prevent overlapping modifying workers and revalidate consumers after integration.
- Performance receives representative evidence; missing tools remain unverified, with no broad speed claim. Preserve failures and remeasure comparable final work after semantic changes.
- TDD retains independent inventory and separate 95% line/branch floors; missing branch metrics or below-gate legacy coverage never pass. Dead-source inventory changes remain explicit.
- Functional decisions, strict Python and the 500-line code maximum apply throughout. UI/copy, production readiness and commit delivery are conditional on actual scope.
- Deliver one prioritized ledger and per-lens verdict with final integrated checks. No quotas, invented blanket pass or exhaustive security/correctness claim.
- Audit-stack routing loads every core lens once, plus actual languages; unrelated single audits and dry-run operations do not invoke the aggregate.

Structural routing/build validation is separate from a target-application audit and real host invocation. Full audits need their own observed reachability, security, coverage, performance, integration and applicable rendered/release evidence.

## Conditional repair interactions

references/repair-interactions.md covers shared findings and conflicting remedies without creating additional ledger schemas. An export-cache defect reported by security, DRY and performance receives one coherent owner/repair while retaining separate isolation, representation and measurement obligations. Removing a cache may close disclosure but leaves its latency impact unmeasured until equivalent work is observed. Later integrations invalidate affected benchmarks and coverage; old passes are not relabeled. Deadness precedes extraction, distinct external enforcement survives consolidation, and unavailable measurements remain explicit gaps.
