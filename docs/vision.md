# Proofwork: skill compression

Proofwork makes the craft of building software accessible through intent, taste and judgment. A person describes what they want, works with a concrete result and refines it. The plugin supplies the engineering discipline needed to make that result dependable.

Our north star: **a person can turn a clear intention into useful, distinctive, verified software without having to manage the engineering machinery themselves.**

The phone-camera analogy captures the shift we want: accessible tools let more people practice a craft through creative choices. It is a product direction, not evidence that engineering expertise will disappear. Engineering knowledge continues to shape implementation, diagnosis and verification; Proofwork carries more of that burden so the user can concentrate on what is worth making.

## What the user owns

Purpose, audience, taste, priorities and consequential choices remain with the person. They can say who the product serves, what feels wrong, what must be preserved and which tradeoff they prefer. Technical users can inspect or direct implementation at any time. Learning is welcome; prior expertise is not an entrance requirement.

A user should not need to know the names of our skills, pick the test strategy, coordinate workers or specify an architectural pattern to receive disciplined work. Start through use-proofwork with an ordinary request. Specialist commands remain available for focused work and expert control.

## What Proofwork owns

Translate intent into observable outcomes; choose relevant skills from the actual task; make proportionate implementation decisions; integrate the work; challenge it; and collect evidence. Use simple adequate tools and preserve existing contracts. Parallelism and model selection serve an uncertainty or independent slice, rather than becoming work the user must orchestrate.

Reveal a technical decision when it changes experience, cost, data ownership, recovery, security or an established requirement. Give a recommendation, its practical consequence and the material unknown. Resolve routine reversible choices from available evidence. Ask only when an unanswered fact or consequential choice changes the result, or when authority is genuinely missing.

## The creative loop

1. Understand the intended experience and inspect the existing product.
2. Make the smallest coherent, reviewable slice within authorized scope.
3. Let the user react to actual behavior, content and appearance where tools permit.
4. Translate that reaction into revised criteria and implementation; preserve unaffected work.
5. Verify the integrated outcome and explain what is proved, uncertain and left to operate.

A slice is not permission to ship a broken production workflow. Unavailable rendering leaves appearance unverified. A confident narrative or passing package build cannot stand in for a demonstrated user journey.

## Finished means

The intended journey works on the current artifact; the result expresses the agreed product character; consequential failure paths and preserved contracts have appropriate evidence; required gates and material findings are settled; and authorized delivery is complete. The person can understand the outcome, remaining limits and their operating responsibility without decoding an agent transcript. Missing evidence remains a gap, even when the result looks convincing.

Evaluate skill compression through paired, comparable tasks: can a newcomer reach a verified result without naming the implementation technique? Record avoidable technical decisions handed back to the user, clarification rounds, time to a useful reviewable slice, recovery from corrections and failures, and defects found in the delivered behavior. Explain counts in task context; no invented universal score or improvement claim. Expert inspection, honesty and safety remain necessary acceptance conditions.

## Product decisions this rules out

Do not grow the command list merely to appear capable, require stack vocabulary in the initial brief, turn every small request into an engineering questionnaire, conceal unresolved risks for a smooth interaction, or substitute attractive output for correctness. Deep specialist skills belong behind precise routing and progressive disclosure. The user-facing experience should become easier as the engineering underneath becomes more dependable.

This is the current product goal. Existing host permissions, scope, pure-decision defaults, strict typing, coverage and code-size requirements remain in force. Skill compression changes who carries the cognitive burden; it does not create authority or relax evidence.
