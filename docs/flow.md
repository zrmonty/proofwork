# Proofwork as one workflow

Describe the outcome through use-proofwork. The entry inspects current context, chooses proportionate guidance and owns the engineering detail. Users need not select skills, plan workers or configure models. Expert procedure names and tier overrides remain available.

| Phase | Work | Carry forward |
| --- | --- | --- |
| Understand | Relevant instructions, current behavior, accepted intent and constraints | One objective, preserved contracts and actual authority |
| Select | Explained route, named guide, principles and preparation | Current stage, appropriate tier and observable criteria |
| Resolve uncertainty | A local probe or bounded candidate comparison when needed | Actual observations and selected approach |
| Change | Direct implementation or explicitly owned independent slices | Current artifact, affected consumers and meaningful checks |
| Challenge | Applicable lenses and independent review proportional to consequence | One disposition list and rechecked repairs |
| Deliver | Clear explanation with reproducible evidence | What passed, what remains uncertain and operator-owned work |
| Resume | Bound checkpoint, live checkout/workers and uncertain effects | The actual next stage, without replaying settled work |

Read the [stage handoff contract](../shared/skills/use-proofwork/references/handoffs.md) for interacting skills. Referenced guidance adds its contract to the current task; it does not start a second root, run, reviewer panel or scheduler. Explore-options owns candidate acceptance, Option Arena organizes isolation and dispatch, performance-increase owns measurement validity, and Measure Loop owns repeated experiments. Challenge Review feeds existing audit/structural verdicts.

Language guidance follows changed files and workload. Functional extraction is conditional on real state/retry/concurrency/cache behavior and its extraction test, with incumbent style first. Clear naming and caller-data ownership remain core. Python strict typing, meaningful separate 95% line/branch gates and actual before/after performance evidence remain intact. There is no universal file/function line ceiling.

Setup happens only for relevant unknown capabilities. Standard work does not load worker-only instructions. Assigned workers receive those instructions with their ownership contract; the coordinator remains responsible for integration. Optional configured model roles preserve account/session policy and must be observed at dispatch. Unsupported independence stays a gap rather than a fabricated panel.

Plain routing, explained routing, comparative inputs and optional prompt hooks share intent normalization and verification decisions. Root invocation prefixes do not change the task stage. Read-only requests stay read-only. Question-shaped architecture decisions remain decisions, while current-flow explanations remain investigation. Mixed review and repair selects a modifying guide and behavioral verification. Explicit procedure names cannot lower a risk floor.

Current subtask rerouting preserves accepted intent. Checkpoints retain compatible stage identifiers, objective, ownership and criteria. Resume loads recovery guidance before choosing the next action; its placeholder route is not a recovered checkpoint. Required recovery text counts initially. Light work needs no ledger. Full work records checkpoints and current-artifact evidence; preflight reads readiness without changing it.

Local success, staging readiness and verified live operation remain different evidence states. No workflow grants deployment, credential changes or publication authority. A limitation yields useful verified work plus a concrete remaining action. It never becomes a confident completion claim.

The [integration verification](../evals/results/integrated-flow-20261010.json) records executed routing, checkpoint/evidence and package checks. Live agent adherence and native continuation are separate unverified boundaries.
